# EACP load benchmark

MASTER_PLAN §104 measured, under the rules of §105: every figure below comes from the raw results in
[`docs/benchmarks/`](benchmarks/), and the tables between the markers are generated from them
(`go run ./cmd/eacp-bench report --out docs/BENCHMARKS.md docs/benchmarks/baseline-*.json`).
`TestBenchmarksDocMatchesBaseline` fails if the tables are edited by hand. How it works:
`docs/superpowers/specs/2026-09-28-load-benchmark-design.md`.

Each PDP ran on a fresh, isolated compose stack (`scripts/bench.sh`). Agents were registered cumulatively
(100, 1,000, 5,000, 10,000); each has its own key, allowlist and THB and USD budget accounts. At each count, load is
open-loop: requests leave at a fixed rate from uniformly random agents, whether or not earlier ones were answered,
and every latency is measured from the moment a request was due. Each step has a 10 s warm-up and a 60 s measurement;
the rate climbs through 25, 50, 100, 200, 400 and 800/s and stops after the first step that is saturated or cannot
drain its backlog within 5 minutes. Stage times come from PostgreSQL's audit journal, never from the client's clock.

## Findings

These notes quote the tables above; they add no figure of their own.

- **Registered agents are not the limit.** Every agent count sustained 25 actions/s under both PDPs. Local
  end-to-end latency is 121.0 / 302.3 / 344.1 ms at 100 agents and 120.8 / 305.0 / 351.4 ms at 10000 agents.
  Admission grows slowly with the registry (P50 37.6 ms at 100 agents, 62.0 ms at 10000).
- **The limit is the execution worker's claim loop, somewhere between 25 and 50 actions/s.** The rate ladder has no
  step between them, so the report can only say 25. At 50/s, admission and governance stay fast (local governance P99
  22.5 to 26.8 ms), but queue wait grows to minutes, and completions *fall* below the 25/s level (local 12.0 to
  9.8/s, AGT 8.8 to 6.7/s) as the backlog grows. PostgreSQL's CPU rises (local mean 117.5% at 100 agents and 25/s,
  372.8% at 10000 agents and 50/s) while the worker's falls (17.8% to 10.4%).
  Reading the code, not measuring it: one worker leases actions one at a time
  (`internal/worker/worker.go`, `claim`), each lease being the fairness query plus a claim transaction, and that
  query ranks the whole queued backlog. So one worker's claim rate is bounded by that round trip, and the round trip
  lengthens as the queue grows. Batched claims, or several workers, are the likely remedy; neither is measured here.
- **The AGT sidecar dominates admission latency.** At 100 agents and 25/s, governance is 12.7 / 16.0 / 19.1 ms
  with the local PDP and 81.2 / 94.3 / 103.9 ms through the sidecar, and admission is 37.6 against 177.1 ms at P50.
  The sidecar used 125.0% CPU at that rate. Throughput at 25/s is the same (23.8 and 23.7 completed/s): the claim loop, not
  governance, is the bottleneck.
- **Three AGT steps at 50/s are `incomplete`**: their backlog (open 711, 608 and 829 actions) had not drained after
  5 minutes. That backlog was still draining during the next level's setup and first step. Those 25/s steps still
  met every threshold, but the first LLM step of that run (25/s, P99 64.3 ms) overlapped it; the later LLM rows (P99
  20.2, 24.2, 30.5 ms) did not.
- **Budget reservation and idempotency stay cheap.** At sustainable rates `eacp.budget_reserve` averaged 2.668 to
  3.075 ms locally and 4.176 to 4.540 ms under AGT. An idempotent replay answers with a P99 of 5.0 to 10.5 ms at those rates. Every run had 0 duplicate keys, 0 errors and 0 429s.
- **The LLM gateway sustained 200 calls/s**, the highest step offered, with no errors. Client latency against a
  fake provider that answers immediately is 17.1 / 43.9 / 87.5 ms in the local run and 16.7 / 22.6 / 30.5 ms in the
  AGT run. The ledger's admit-to-settle time is 8.1 and 7.7 ms at P50. The gateway's own ceiling was not reached.
- **Setup** went from 5000 to 10000 agents in 64.4 s (local) and 68.8 s (AGT). Each agent takes 13 API calls: its
  registry, key and budget writes, each approved by a second person. Each Setup row is the time to reach its
  agent count from the previous row.
- **Caveats.** One machine with Docker Desktop limited to 8 CPUs; the idle development stack ran alongside. The run
  was made from commit `c5d42f5` with uncommitted documentation and test changes only: the benchmark code is that
  commit. One tenant and one worker; several tenants, workers or replicas are not measured yet.
